# M2 admission hot-path measurement — 28 September 2026

This is a **local diagnostic**, not a production capacity result or approval to change transaction isolation. The reproducible harness is `npm run benchmark:admission` in [benchmark-admission.mjs](../../scripts/benchmark-admission.mjs). It calls the M1 admission service/repository against PostgreSQL, creating isolated applications, connections, profiles, and budget accounts; each case issues 100 unique admissions without provider calls. The harness removes its own rows after every case. A post-run query found zero benchmark applications, connections, executions, budgets, or rate windows.

Environment: Windows workstation, Node v24.11.1, PostgreSQL 15.5, Prisma/pg adapter, pool max **6**, statement timeout **5 s**. Each case uses one budget account per application. `shards=1` directs all 100 admissions to one application/connection/account; `shards=8` spreads them evenly across eight independent sets. p95/p99 are nearest-rank values in milliseconds. `BEGIN` counts include transactions retried internally by admission. Pool acquisition includes connection overhead. Lock-statement duration includes query execution and network round trip; PostgreSQL lock wait events were sampled every 10 ms and can miss short waits.

Both files record the compiled repository hash and isolation. The source and compiled API were restored to Serializable after the experiment. All **55/55** PostgreSQL integration tests passed with the temporary isolation, including existing concurrent admission/cap tests; those tests do not prove every management/admission race safe.

Two earlier Serializable probes with the developing harness showed substantial run-to-run variance: at 24 workers/eight shards, p95 was 1806 ms and 4511 ms. The final matched run above is therefore useful for identifying retry amplification and testing a candidate, not for claiming a stable speedup or production SLO. All cases in all runs accepted 100/100 requests.

The current transaction takes application and route advisory locks, counts active executions, updates rate windows, and locks budget rows. At concurrency 8–24, the observed `BEGIN` count exceeds committed admissions several-fold, even when work is spread across eight applications. Local `EXPLAIN` after fixture cleanup chose sequential scans for both capacity counts. PostgreSQL documents that a sequential scan in a Serializable transaction requires a relation-level predicate lock and can increase serialization failures. This is a plausible contributor, **not a proven attribution** for every retry in this run. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/15/transaction-iso.html), [advisory locks](https://www.postgresql.org/docs/15/explicit-locking.html).

The temporary Read Committed result is promising but cannot be shipped as a one-line change. Operator management can change application/connection limits and routing policy without taking the admission advisory locks. Those races, plus shared quota-group changes and cancel/completion interleavings, need a lock-order and linearization review with deterministic tests before relaxing isolation. The next decision is whether to make all relevant writers participate in a narrower explicit-lock protocol, or retain Serializable and reduce broad predicate reads/retry amplification with measured SQL/index or permit-row changes. No Redis shedder or raw-SQL rewrite is justified by this single local run.
