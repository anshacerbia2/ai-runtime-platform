# Native runsc process transport

**20 October 2026: experimental M3 host component, not production host activation or O03 closure.** [`RunscProcessClient`](../../apps/runner/src/runsc-process-client.ts) replaces ad hoc CLI calls and attached monitors in the driver portion of [real gVisor conformance](../security/SANDBOX-EVALUATION.md#linux-vmvps-experiment). It composes with the [bundle producer](VERIFIED-RUNSC-BUNDLES.md), [launch store](RUNSC-LAUNCH-STORE.md), and [driver/supervisor](RUNSC-DRIVER.md). ADR-0011 and the approved architecture remain unchanged.

## Trusted installation and command surface

The host supplies canonical executable/state/bundle paths, an independently approved executable SHA-256 and command/run deadlines. Linux is required before filesystem access. The entrypoint is a regular, single-link, owner-executable file owned by the effective UID, with no group/world writes or special permission bits. Its bytes are hashed in 64 KiB reads, up to 256 MiB. The executable parent is owned and not group/world writable; state/bundle roots are disjoint private 0700 directories. Symlinks/aliases and executable paths inside either mutable root are rejected. Held FDs and synchronous device/inode/mode/ownership checks detect path replacement immediately before each spawn; executable size/mtime/ctime drift is also rejected.

These checks are **not full distribution approval or protection from a trusted host administrator**. The current [gVisor distribution](https://gvisor.dev/docs/user_guide/install/) has adjacent `gvisor-bin/` sidecars; the independently verified package installed by CI remains responsible for their provenance. The client does not install/download runtime code, approve sidecars/signatures, resolve revocations, protect writable ancestors from another host principal, or create an exclusive runtime owner. Production composition must secure the complete installation and private paths through execution.

Only list, exact-record state, all-process TERM/KILL, forced delete, and attached run are exposed. Every record must have the deterministic assignment name and bundle path beneath the configured root. Flags are fixed to `--platform=systrap --network=none`; there is no shell, caller argv/env override, stdin input, detached start, host PID kill API or fallback execution. Children receive only fixed PATH/LANG, not the worker environment. State output still requires the full binding validation performed by the trusted host/driver; a transport response alone cannot authorize a signal or certify absence.

## Bounds and uncertainty

The supervisor's authority/stop/drain guard reaches the client through the driver and host. The client rechecks it after synchronous filesystem validation, immediately before the OS spawn: synchronous I/O can also consume a lease. A denied or throwing guard does not spawn; it retains the attempted name without inventing transport loss. There is no await, queue or filesystem operation between this last guard and spawn.

At most four control commands and eight attached monitors can be active; excess intake is rejected without a queue. At most 256 assignment names may be attempted during one client lifetime, and each is sealed synchronously before spawn, including failed attempts. Reopening a new client does not preserve those local names; durable launch reservations and exclusive host ownership remain mandatory to prevent rerun.

Control replies have a combined stdout/stderr limit of 64 KiB and strict UTF-8/JSON parsing. Empty-list `null` is explicit; malformed/duplicate/oversize list entries or null/nonobject state are rejected. Attached output is drained without retaining/returning guest bytes, with a combined one MiB lifetime limit. Child stderr and raw error output never appear in public errors. Numeric nonzero CLI status is rejected for control operations; a numeric attached-monitor exit remains `REAPED` with its actual code, not an execution result or invented transport loss.

Configured control deadlines are 10–30000 ms and run deadlines 10–3600000 ms. Timeout/output/transport failure kills only the owned CLI child, preserves `LOST`, and blocks further runs; control inspection/cleanup remains available. Completion waits for the original child exit (or a known failed spawn), not a kill acknowledgement. If it cannot be reaped, the operation stays pending and cannot release capacity. Event-loop timers are not an external hard realtime watchdog.

For attached runs, original-child exit is independent of stdout pipe EOF. Control replies instead drain through close before decoding; their deadline still applies if descendants retain pipes after the original child exits. This follows Node's separate [exit/close event contract](https://github.com/nodejs/node/blob/v24.11.1/doc/api/child_process.md#event-exit). `close()` seals intake, drains accepted operations, and closes held FDs; it does not kill guest trees, certify stop, release ownership locks, retire reservations or authorize retry.

## Evidence and remaining work

The later [native cgroup/live-owner crash checkpoint](NATIVE-CGROUP-OWNER-CRASH.md) now kills an owner while this client's monitor and real sandbox remain live. Stale storage ownership blocks reopen and fresh runtime paths; explicit fixture cleanup requires kernel/runtime/original-monitor disappearance while preserving the lock. This advances crash evidence without adding production host takeover or new monitor exit status.

Linux native tests use a separately pinned inert CLI double for environment/argv, approval/root validation, duplicate attempts, intake/close, timeout/output bounds, invalid replies, entrypoint/root replacement, spawn failure and monitor status. Windows tests prove unsupported-host refusal; native cases are explicitly skipped there. `npm run test:unit` includes both. Real gVisor driver conformance now uses this client for attached run/state/signals/delete; an additional one-second monitor-deadline experiment retains LOST, prevents rerun/new reservations, and requires explicit whole-subtree cleanup. Monitor-less missing state stays UNKNOWN, while an observed started binding still needs independent trusted delete, empty subtree and fresh absence.

This is not a production `RunscSandboxHost`. Cgroup inspection and readiness/ownership composition remain in the disposable fixture. No live-owner process-crash handoff, stale-lock takeover, full worker/shared-store fencing, trusted release/credential delivery, Claude bridge, broker egress, actual VPS approval or production activation is claimed. O03/O06/O14/O15 stay open. The next host work is exclusive lifecycle/recovery composition and live-orphan/crash proof; production release and scoped runtime delivery remain dependencies.
