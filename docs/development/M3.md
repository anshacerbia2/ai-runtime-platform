Job CI `gvisor-conformance` mem-pin runtime package/checksum, menguji lifecycle/isolation/cgroup/tmpfs caps, dan mencatat host/binary fingerprints. Windows menolak probe sebelum mutation. M3 masih dalam pembangunan. Checkout lokal dapat menjalankan API/Web M0–M2 dan menguji fondasi runner/dispatch terhadap PostgreSQL. Plugin validation/materialization, signature verification, lease-scoped delivery, dan worker HTTP handoff tersedia sebagai komponen programatik. Belum ada agent runner Claude, sandbox produksi, atau endpoint payload/plugin aktif yang membuat `agent_execute` berjalan end-to-end.

Adapter HTTP binary untuk payload dan plugin runner sudah diuji dalam komposisi Nest terisolasi. Keduanya menuntut otoritas runner, kontrak request yang ketat, batas respons masing-masing 1 MiB dan 16 MiB, serta respons tanpa cache. Adapter dapat memakai service internal yang memeriksa lease/binding pada kedua sisi decrypt atau download. Controller belum terdaftar di `AppModule`, sehingga route tidak tersedia dari API lokal/produksi. Production KMS/storage dan signer trust/provenance wiring tetap prasyarat aktivasi; test HTTP memakai delivery fixture, bukan membuktikan pengiriman end-to-end.

Daftar runner operator `/api/v1/runners` menampilkan `liveness` terpisah dari `status`. Setelah heartbeat dengan revision registrasi terkini, liveness menjadi `ALIVE`; tanpa presence terkini menjadi `OFFLINE`. Jika coordination store gagal dibaca, UI/API menerima `UNKNOWN`, bukan menyimpulkan runner offline. Liveness tidak mengizinkan retry/reassignment atas attempt yang sudah `ORPHAN_SUSPENDED`.

Paket runner memiliki `LocalSandboxSupervisor` sebagai boundary lifecycle lokal untuk adapter sandbox yang kelak dipilih. Ia mengikat satu launch ke assignment/boot/generation/epoch, menahan duplicate launch, meminta stop lalu eskalasi berbatas waktu, dan hanya menghasilkan `TERMINATED` bila adapter membuktikan seluruh sandbox/process tree sudah exit. Port `recover` dapat menemukan sandbox dari proses supervisor sebelumnya; binding lengkap diperiksa sebelum sinyal stop dikirim. Launch/lookup terlambat, binding yang tidak cocok, kegagalan inspeksi, atau sandbox yang tidak ditemukan menghasilkan `UNCONFIRMED`. Ini belum meluncurkan proses produksi, belum membuktikan efek eksternal selesai, dan belum memberi izin reassignment.

Untuk drain lokal, `quiesce()` langsung menolak launch baru dan mengembalikan snapshot assignment yang sudah tercatat tanpa menghentikan pekerjaan aktif. Pemilik lifecycle memutuskan deadline in-flight; setelah cancel atau deadline, `stopTracked()` meminta stop untuk snapshot itu dan mengembalikan bukti per assignment. Ini belum terhubung ke drain pool, cancel intent durable, atau shutdown runner produksi.

Supervisor lokal menahan maksimal 256 identitas sepanjang umur proses agar tidak tumbuh tanpa batas. Worker dapat menyimpan local stop evidence melalui outcome journal opsional di bawah. Coordinator receipt/reconciliation dan retirement protocol untuk melepas identitas dengan aman belum tersedia, sehingga primitive ini belum cocok untuk worker produksi berumur panjang.

`RunnerLeaseGate` adalah guard lokal setelah aktivasi lease berhasil. Deadline dihitung dari waktu monotonic **sebelum request aktivasi/renew dikirim**, sehingga latensi respons tidak menambah umur lease lokal. Ia menolak langkah provider/tool baru setelah deadline atau renew gagal, membatasi waktu renew, dan meminta stop sandbox sekali; respons renew yang terlambat tidak membuka gate kembali. Pemanggil masih harus menjadwalkan renew, memeriksa guard sebelum **setiap** langkah baru, dan mengikat port renew ke token/boot/nonce yang tepat. Belum ada proses runner atau adapter HTTP produksi yang memakai guard ini; stop lokal bukan bukti efek eksternal selesai.

`RunnerLeaseLoop` sekarang menjadwalkan renew dari waktu kirim aktivasi/renew terakhir (default 5 detik) dan memasang watchdog pada deadline lease. Renewal gagal, timer gagal dipasang, atau event loop baru bangun setelah deadline menutup gate dan meminta stop. Pemilik lifecycle wajib memanggil `start()` segera setelah aktivasi berhasil dan `stop()` saat cancel/fence/shutdown; loop ini belum dihubungkan ke proses runner produksi. Check gate sebelum setiap langkah baru tetap wajib.

`RunnerLeaseHttpClient` menyediakan transport aktivasi/renew yang terikat ke satu command assignment/boot/registration revision/nonce. Ia mengirim satu POST ke origin tepercaya, menolak redirect atau respons di luar kontrak, membatasi ukuran 64 KiB dan durasi request, serta tidak mengulang hasil ambigu. `activate()` mengembalikan timestamp monotonic sebelum credential/network untuk dipakai `RunnerLeaseGate` dengan clock yang sama.

`RunnerAssignmentLifecycle` sekarang mengomposisikan HTTP client, gate, renewal loop, dan supervisor untuk **satu assignment dalam satu proses**. Identitas sandbox diturunkan dari command lease yang divalidasi dan owner dari trusted runner composition. `start()` konkuren pada instance yang sama berbagi satu aktivasi/launch; renewal dan expiry watchdog harus terpasang sebelum sandbox diluncurkan. Guard supervisor memeriksa gate lagi pada microtask yang benar-benar memanggil driver, sehingga expiry di antara enqueue dan dispatch menolak launch. Launch memiliki deadline lokal (default 10 detik, maksimum 30 detik), termasuk pemeriksaan monotonic setelah respons. `runStep()` memeriksa gate tepat sebelum memanggil langkah trusted runtime. `stop()` menolak langkah baru dan meng-abort sinyal kooperatif sebelum menunggu cleanup. Cancel saat aktivasi/launch, renew gagal, deadline lewat, dan respons terlambat tidak dapat menghidupkan instance kembali. Hasil langkah yang sudah in-flight tetap dikembalikan agar caller dapat merekonsiliasi efek/usage; hasil itu bukan authoritative completion.

Langkah runtime wajib melewati `runStep()` pada setiap dispatch baru, serta menghormati abort sebelum melakukan I/O setelah await. Fixture HTTP loopback menguji transport lease nyata terhadap server uji; sandbox/runtime tetap fixture, bukan bukti isolasi atau live API/Redis/PostgreSQL end-to-end.

## Application tool-operation status

Backend aplikasi dapat membaca operasi milik execution-nya melalui GET `/v1/executions/:id/tool-operations` dan `/v1/executions/:id/tool-operations/:operationId`, dengan application bearer berscope `execution:read`. Scope aplikasi diturunkan dari principal, bukan query/body. Operator dan runner ditolak. Missing/foreign ID menghasilkan 404 yang sama. Execution yang sah tanpa operasi menghasilkan list kosong. Route berada pada module tersendiri dan terdaftar juga di komposisi `api-production`, tanpa mengaktifkan mutating tool broker atau payload delivery.

List membatasi `limit` 1–100 (default 25), mengurutkan UUID operation, dan menggunakan optional `after`/response `nextAfter`. Cursor hanya batas keyset, tidak memberikan akses ke execution/aplikasi lain. `consistency: live-keyset` berarti tiap halaman membaca kondisi saat itu; insertion dengan UUID sebelum cursor dapat terlewat dan perubahan status bukan snapshot lintas halaman. Tidak ada polling/timer atau akses browser/BFF otomatis.

Status yang ditampilkan adalah observasi durable `PREPARED|DISPATCHING|UNKNOWN|COMMITTED|NO_EFFECT`, bukan remote query baru. Terminal receiver states memerlukan receipt ref/digest; state lain mempunyai `receipt: null`. `PREPARED` belum menjamin aman retry; `DISPATCHING`/`UNKNOWN` tidak menyatakan no effect. Retention deadline hanyalah metadata intent; berlalunya waktu tidak mengubah UNKNOWN menjadi NO_EFFECT atau menghapus receipt yang sudah tersimpan. Receipt ref adalah identifier, bukan signed access grant atau izin fetch arbitrary URL. Endpoint tidak mengirim input bytes, assignment/boot/nonce/epoch/generation, receiver idempotency key, credential atau storage path.

Pembacaan tetap tersedia setelah cancel/fence, tanpa live runner lease. Ia tidak memanggil receiver, mengubah operation/execution/attempt, mempromosikan artifact, melepas reservation atau mem-post ledger. Status eksternal dan accounting tetap terpisah. Aplikasi memakai operation identity dan observasi ini untuk workflow rekonsiliasinya; endpoint tidak melakukan kompensasi bisnis.

Recipe: `npm test`, `npm run test:unit`, dan `npm run test:integration`. Kasus tool-effect pada `dispatch-envelope.integration.test.ts` membuat intent/status melalui kernel PostgreSQL, sengaja fence assignment, lalu membaca kelima state melalui dua API. Ia memeriksa scoped 404/403/401, query/cursor bounds, pagination tanpa duplikasi pada dataset tetap, expired retention, unchanged DB snapshots, serta receiver-call counts. Auth dan receiver tetap fixture; live receiver conformance, authorized invocation/budget/approval grants, runner-to-broker integration dan sandbox/Claude belum dibuktikan. Tidak ada perubahan ADR atau keputusan O03/O14.

File-file suite PostgreSQL memakai schema bersama dan sekarang dijalankan berurutan (`--test-concurrency=1`). Fixture dispatch mempunyai private in-memory lease store serta sengaja mengubah timestamp menjadi expired; reaper dari API file lain tidak mempunyai lease tersebut dan dapat mem-fence fixture yang masih diuji. Eksekusi paralel mereproduksi kegagalan lease/claim, sementara serial meluluskan 71/71. Ini isolasi antar-file test, bukan serialisasi request produksi: race/admission/concurrent dedup di dalam test tetap konkuren, dan gate worker HTTP dengan shared Redis tetap terpisah. HTTP status assertions dimulai setelah fixture sengaja di-fence agar tidak mencampur live lease privat dengan reaper API.

## Bootstrap worker programatik

`RunnerWorker` mengikat runner yang **sudah terdaftar** ke owner dan registration revision dari trusted host composition. Satu instance menghasilkan satu boot UUID baru yang tetap sepanjang umurnya. `start()` menunggu heartbeat yang cocok sebelum menjadwalkan claim; heartbeat berjalan terpisah dari claim/startup pada interval 5 detik, dihitung dari waktu kirim request. Claim diserialisasi dengan interval default 1 detik (100–5000 ms). Capacity lokal mencakup startup dan pekerjaan aktif. Setiap assignment menyimpan satu lifecycle dan nonce; replay grant, termasuk sesudah local completion, tidak boleh menjalankan runtime kedua kali. Grant berubah dengan ID sama atau scope berbeda menghentikan worker.

Alurnya: heartbeat → claim → activation/renewal → guarded driver launch → scoped `STARTED` report → trusted runtime callback. Callback baru dipanggil setelah acknowledgement start cocok dengan token, owner, dan state. Guard launch serta setiap langkah runtime juga memeriksa deadline presence proses, sehingga lease assignment baru tidak membolehkan launch setelah presence lama expired. Heartbeat gagal, clock invalid, atau kegagalan timer menghentikan claim dan menutup semua lifecycle. Claim dengan outcome transport sementara/ambigu hanya dipoll lagi pada interval berikutnya memakai boot yang sama; transport sendiri tidak retry. Report start yang ambigu menghentikan assignment lokal tanpa retry runtime atau menganggap transaksi server rollback.

`quiesce()` membatalkan claim yang masih pending dan menolak launch baru sambil mempertahankan heartbeat serta pekerjaan yang sudah berjalan. `drain(graceMs)` memasang satu deadline monotonic, maksimum 30 detik, yang tidak dapat diperpanjang oleh panggilan ulang. Setelah pekerjaan selesai atau grace habis, `stop()` menutup gate dan menjalankan cleanup supervisor yang berbatas waktu; waktu cleanup berada di luar grace. `shutdownSignal` opsional menjalankan drain yang sama dengan `drainGraceMs` (default 5 detik); host composition menerjemahkan SIGTERM/deployment shutdown ke sinyal ini. Bootstrap dengan sinyal yang sudah aborted tidak mengirim HTTP. Hasil stop adalah bukti lokal, terpisah dari remote effect dan financial settlement.

Registry lokal dibatasi `maxTracked` (maksimum 256, selaras dengan supervisor). Identitas assignment yang selesai tetap ditahan; cleanup `UNCONFIRMED` tetap memakai slot capacity. Tidak ada eviction otomatis sebelum retirement/reconciliation protocol tersedia, sehingga worker ini belum siap menjadi daemon produksi berumur panjang. Runtime callback menerima metadata grant dan context gate/abort, tanpa kredensial object store, KMS, atau database. Callback wajib mempertahankan evidence efek/usage yang datang terlambat. Return `void` tidak membuat proposal; typed result return sekarang dapat mengirim satu result proposal, tetap terpisah dari completion dan settlement.

Ini merupakan bootstrap programatik dan harness, belum executable/deployment production. Host masih harus menyediakan registration/credential delivery, adapter sandbox yang approved, dan trusted runtime bridge. Fast cancel/fence notification, aktivasi produksi payload/plugin delivery, Claude SDK, production collector composition untuk failed reporting, dan stop-receipt reconciliation masih pending. Tidak ada default yang menjalankan plugin di host/API process.

### Durable authority, result proposal, dan late evidence

`context.runStep()` sekarang memanggil `RunnerAssignmentLifecycle.checkAuthority()` sebelum langkah provider/tool baru. Ia memakai endpoint aktivasi/renew yang sudah ada dengan exact boot/lease command; coordinator memeriksa cancel intent dan durable generation/epoch/runner/plugin policy di PostgreSQL, serta presence dan lease Redis. Ini satu request preflight tambahan per dispatch, termasuk lock/read PostgreSQL pada jalur renew yang sudah ada; biaya throughput belum diukur. Preflight tidak memperpanjang deadline gate lokal. Gate lease/presence/drain diperiksa lagi setelah await sebelum callback I/O. Request gagal/timeout menutup lifecycle. Renew periodik nominal 5 detik juga membawa pemeriksaan durable itu selama operasi in-flight; latensi transport dan scheduling tetap menambah waktu deteksi. Tidak ada endpoint polling cancel atau periodic heartbeat write PostgreSQL baru.

Cancel yang commit sebelum pemeriksaan durable menolak langkah baru. Preflight dan dispatch eksternal bukan satu transaksi: cancel yang bersaing setelah pemeriksaan tidak menarik kembali call yang sudah diizinkan/in-flight. Abort/stop tidak membuktikan provider/tool membatalkan efek atau biaya. Trusted bridge masih harus menghormati abort setelah await, mempertahankan operation lineage, dan menggunakan broker/idempotency receiver saat mutasi diaktifkan.

Trusted runtime boleh return `RunnerResultProposal` (`outcome`, digest, artifact IDs, summary). Worker menutup context untuk dispatch/input baru saat runtime return, menolak proposal bila ada langkah/input/evidence yang belum di-await, lalu mengirim tepat satu `result.proposed` dengan token dan lease tertahan. ACK harus cocok untuk seluruh scope dan berstatus `RESULT_PROPOSED`. Return `void`, exception, malformed result, stopped gate, atau cancel tidak menghasilkan synthetic success/failure proposal. ACK ambigu tidak diulang otomatis dan tidak menjalankan ulang runtime; trusted host/reconciler harus mempertahankan candidate untuk pemeriksaan durable. Proposal bukan authoritative execution completion, artifact promotion, atau financial settlement.

`context.reportEvidence(usage, signal?)` mengirim `UsageCommand` ke intake yang sudah ada, memakai execution/attempt/token lama tanpa live lease. Jalur ini tetap tersedia setelah cancel, fence, runtime return, atau local worker stop. Response harus HTTP 202 dengan `QUARANTINED`, bukan bukti verified usage/posted ledger. Source event ID/revision dan unknown units dipertahankan; explicit same-event replay dapat memakai dedup server, tanpa retry otomatis. Worker membatasi delapan request evidence in-flight; collector opsional di bawah menyediakan durable spool. Pending evidence menolak paid step baru; kegagalan, invalid receipt, atau overflow menutup assignment. Error dikembalikan ke bridge agar evidence yang belum tersimpan tetap dipertahankan; tidak diganti nol atau dibuang sebagai sukses. Signal evidence berasal dari caller dan terpisah dari signal stop assignment. Production collector composition, host lifetime untuk flush, verification/settlement, stop receipts, dan retirement tetap harus dibangun.

### Bounded evidence collector dan encrypted file spool

[`RunnerEvidenceCollector`](../../apps/runner/src/runner-evidence-collector.ts) menyediakan write-before-send untuk late usage intake sesuai [dependency matrix](../reliability/OWNERSHIP-RECOVERY.md). Trusted host dapat memasoknya melalui `RunnerWorkerOptions.evidenceCollector`; runner ID dan owner harus cocok. Evidence divalidasi, dienkripsi, dan disimpan durable sebelum POST ke endpoint quarantine existing. Token assignment lama dan seluruh `UsageCommand`, termasuk `null`/unknown usage, dipertahankan. Nonce, bearer token, credential callback, prompt dan result proposal tidak dimasukkan ke spool; field `reason` tetap berpotensi sensitif dan ikut dienkripsi.

Hanya receipt HTTP 202 `QUARANTINED` valid membolehkan durable deletion. Lost ACK, timeout, abort caller, invalid receipt dan kegagalan delete menahan record atau menyegel collector untuk recovery. Abort caller tidak membatalkan penyimpanan evidence yang sudah diterima collector. Same event/revision dengan isi berbeda ditolak tanpa overwrite; input disnapshot sebelum await. Collector membatasi delapan intake aktif tanpa queue dan maksimal 256 record. Pending intake/backlog atau storage/encryption failure menolak startup, claim/launch dan paid step baru pada worker yang memakai collector, termasuk assignment lain. Report late evidence tetap tersedia setelah worker stop; replay tidak membuka kembali context yang sudah ditutup.

`flush(signal?)` adalah replay eksplisit, berurutan dan bounded, berhenti pada kegagalan pertama. Tidak ada retry timer, rerun runtime, retry proposal, automatic reassignment, completion atau ledger write. Host harus menunggu producer in-flight dan collector report/flush sebelum menutup store; `worker.stop()` sendiri tidak menjamin collector sudah selesai. Intake yang ditolak sebelum append berhasil, termasuk overflow atau KMS/disk unavailable, tetap menjadi tanggung jawab producer untuk dipertahankan. Tanpa collector opsional, bridge tetap memiliki seluruh durable retention seperti checkpoint reporting sebelumnya.

[`FileEvidenceSpool`](../../apps/runner/src/file-evidence-spool.ts) adalah backend programatik opsional untuk Linux. Host menyediakan direktori persistent yang sudah ada, canonical tanpa symlink, owner UID sama dan permission tanpa akses group/other. Exclusive `writer.lock` menolak writer kedua. File ciphertext private ditulis melalui temporary append, file fsync, atomic rename, lalu directory fsync sebelum put berhasil; deletion juga fsync direktori. Batas host wajib eksplisit: 1–256 record, total 1 byte–16 MiB, maksimal 64 KiB ciphertext per record, termasuk encryption metadata. Tidak ada TTL, eviction, penghapusan otomatis evidence unresolved, atau fallback memory/plaintext.

Setelah crash, lock tidak diambil alih berdasarkan PID/umur/TTL. Host/operator harus membuktikan collector lama sudah berhenti dan mendapatkan exclusive ownership direktori sebelum menghapus hanya `writer.lock`, lalu membuka store/collector kembali. Partial append, file asing, symlink, ukuran/permission invalid, ciphertext corrupt, identity/key tidak cocok atau directory fsync yang tidak didukung menolak recovery; record dipertahankan untuk pemeriksaan/reconciliation. Procedure ini tidak membuktikan external effects selesai atau mengizinkan reassignment. Hilangnya node/disk, power-loss storage guarantees, backup/restore dan operator recovery automation belum terbukti.

Host wajib menginjeksi `EvidenceCipher` yang menyediakan authenticated encryption dengan context version/runner/owner/record ID, wrapped-key metadata dan key recovery/rotation. Tidak ada implementation/default key produksi; AES-GCM fixture memakai ephemeral test key saja. Backend file menolak Windows. Operasi filesystem sync sengaja eksplisit; sebelum deployment host harus mengisolasi collector I/O dari event loop worker/lease, memastikan persistent-volume semantics dan retention/deletion O06, serta menyediakan KMS/workload identity O14. Tidak ada environment setting, executable/deployment, production route, atau perubahan keputusan sandbox O03 pada slice ini. Buffer cleanup tidak menjamin penghapusan semua string/copy JavaScript.

Recipe: `node --import tsx --test apps/runner/test/runner-evidence-collector.test.ts apps/runner/test/file-evidence-spool.test.ts apps/runner/test/runner-worker.test.ts`. Windows menjalankan orchestration/worker dan refusal backend; filesystem tests berjalan di Linux quality CI, termasuk SIGKILL setelah durable append dan explicit fenced-owner recovery. Gate `test:runner:http` menambahkan lost committed evidence ACK, encrypted spool reopen dan replay via API B; PostgreSQL harus tetap mempunyai satu quarantine row dan hold 10 unit, tanpa ledger/verified observation atau runtime replay. Ini subset reporting durability, bukan closure production collector/recovery gates.

### Durable result candidate dan local stop journal

[`RunnerOutcomeJournal`](../../apps/runner/src/runner-outcome-journal.ts) memakai port cipher/storage collector, dengan direktori/ownership dan authenticated context terpisah. Host memasok `RunnerWorkerOptions.outcomeJournal` dengan runner ID/owner yang cocok. Reservation ini lokal pada satu writer, bukan admission/capacity authority PostgreSQL.

Typed result valid tanpa unawaited work disimpan terenkripsi sebelum proposal HTTP. Kandidat yang datang setelah local stop juga dipertahankan; guard tetap menolak proposal atau paid step dari context yang ditutup. Append failure menolak proposal HTTP dan menyegel journal. Record memuat token assignment lama, boot/revision, digest/artifact IDs/summary; summary ikut dienkripsi. Nonce, bearer credential, prompt dan callback HTTP tidak disimpan. Tidak ada resend/timer, runtime replay, completion atau settlement. Bahkan setelah ACK valid, kandidat tetap ditahan untuk durable coordinator reconciliation; ACK hilang tidak ditafsirkan sebagai rollback.

Lifecycle abort, runtime finally, dan `worker.stop()` konkuren berbagi satu cleanup/stop record. Record immutable: unknown tidak ditimpa menjadi termination. Pengamatan recovery berikutnya memerlukan protocol terpisah. Hasil stop mempertahankan `evidence` lokal dan menambahkan `durableReceipt: RECORDED|UNAVAILABLE` bila journal dipakai. Field ini hanya status persistence lokal, bukan coordinator ACK atau kesimpulan external effects. Gagal menulis receipt menahan capacity dan quiesce claim tanpa memalsukan hasil inspeksi.

Cipher checkpoint/recovery mempunyai deadline eksplisit `timeoutMs` 100–3000 ms. Respons cipher terlambat dihapus tanpa late append; cleanup tidak menunggu key provider selamanya. Ini tidak membuat synchronous filesystem I/O nonblocking: production host tetap wajib mengisolasi I/O dari event loop lease. Host menunggu producer late candidate dan journal write sebelum menutup store. `worker.stop()` menunggu cleanup/receipt yang tercatat, bukan menjamin runtime tidak kooperatif sudah return atau external receipts selesai. Intake/append yang gagal sebelum durable capture tetap memerlukan retention/reconciliation producer; tidak diklaim sudah tersimpan.

Recovery memvalidasi maksimal 256 record. Journal dengan record proses lama tetap `readyForWork=false`; bootstrap baru ditolak sampai coordinator reconciliation/retirement terotorisasi tersedia. Tidak ada eviction, delete, gate reopen, PID/TTL lock takeover atau reassignment otomatis. Private-directory/fsync/crash-lock/KMS constraints mengikuti backend spool di atas. Journal penuh menolak claim baru; slot assignment yang sudah dicadangkan tetap tersedia. Ini belum daemon produksi berumur panjang.

Linux CI menambah SIGKILL setelah kandidat dan setelah stop: stop record yang tidak ada tetap unknown; `UNCONFIRMED` tidak menjadi synthetic termination. Auth/runtime/sandbox/key masih fixture. Coordinator receipt intake/reconciliation/retirement, persistent-volume/node-loss recovery, production KMS/identity/retention dan sandbox/Claude tetap pending. ### Coordinator stop receipt dan result reconciliation

Coordinator menyediakan dua endpoint machine-only baru: `POST /api/runner/v1/stops` (202) dan `POST /api/runner/v1/results/reconcile` (200). Keduanya memerlukan principal runner dengan `runner:report`, token assignment lama, exact original boot dan revision registrasi saat claim. Tidak ada live lease, Redis presence, nonce atau kondisi runner saat ini yang diperlukan untuk mempertahankan observasi lama. [Migration 0026](../../prisma/migrations/0026_runner_stop_receipts/migration.sql) menyimpan `claim_registration_revision` pada claim baru dan metadata stop di `control.runner_stop_receipts`. Assignment lama tetap nullable: revision historis tidak di-backfill dari registry sekarang; process binding yang belum dapat dibuktikan ditolak, bukan ditebak. Payload/evidence intake existing tidak berubah.

Stop intake hanya menerima kombinasi `TERMINATED` + `GRACEFUL|FORCED|OBSERVED`, atau `UNCONFIRMED` + `null`. PostgreSQL memeriksa scope assignment/execution/attempt/runner/owner/generation/epoch dan original process binding, lalu menyimpan receipt `QUARANTINED`, audit, dan outbox dalam satu transaksi. Identity `(assignment, boot, registration revision)` immutable: replay isi sama mengembalikan receipt ID yang sama; isi berbeda conflict. Stop tidak mengubah compute/external/authority attempt, status execution, assignment generation, reservation, ledger, verified usage atau result pointer. Runner credential dan self-report bukan proof independen bahwa process tree atau remote effects selesai.

Result reconciliation menerima hanya SHA-256 dari canonical seluruh proposal, termasuk summary/artifact IDs; ini bukan field `proposal.digest` yang merupakan digest hasil. Response `MATCHED|NOT_RECORDED|CONFLICT` membandingkan digest dengan proposal yang sudah commit di PostgreSQL, tanpa menulis proposal baru atau mengembalikan isi kandidat. Match dapat tetap benar setelah cancel/fence; `stale` dilaporkan terpisah. `MATCHED` bukan authoritative completion, settlement, verifikasi sandbox atau izin reassignment. Execution `FOR SHARE` memberi satu observation point terhadap report/fence yang memakai `FOR UPDATE`; tidak ada lock DB selama HTTP/provider work.

[`RunnerOutcomeHttpClient`](../../apps/runner/src/runner-outcome-http-client.ts) menyediakan explicit stop/reconcile dari record journal lama. Ia memvalidasi echoed binding/evidence/digest dan status/schema response, memakai trusted origin/deadline yang sama, tanpa retry otomatis atau pengiriman ulang `result.proposed`. Host tetap memiliki lifetime, credential delivery, replay dan pembacaan journal. Receipt maupun digest match **tidak menghapus journal**, tidak membuka `readyForWork`, tidak melepas tombstone/capacity, dan tidak mengaktifkan retirement. Verifier/reconciler dengan proof yang cukup serta retirement protocol tetap dependency berikutnya.

Tes PostgreSQL lokal membuktikan no-record/match/conflict, identity/legacy denial, cancel/fence, registry changes, concurrent dedup, immutable evidence, atomic rollback saat outbox gagal dan absence of authority/financial mutations. Tes HTTP lokal menolak application/operator dan malformed stop evidence. CI `test:runner:http` menambah lost committed stop ACK/replay A→B sesudah lease key dihapus/cancel, satu receipt/outbox dan hold utuh; kasus lost result ACK membaca journal lalu membuktikan canonical match melalui API B tanpa proposal kedua. Auth/runtime/sandbox tetap fixture; tidak ada independent sandbox verification atau production readiness closure. Route baru masuk generated API/OpenAPI, tetap tidak diekspos ke browser/BFF, dan tidak mengubah ADR.

### Payload/plugin handoff ke trusted runtime

Setelah exact `STARTED` acknowledgement, trusted runtime dapat memanggil `context.withInputs(async (inputs, signal) => ...)` **sekali per assignment**. Worker mengunduh payload, kemudian plugin bila profile memakainya, melalui `RunnerDispatchHttpClient`. Setiap request dan callback melewati gate lease/presence/drain lagi. Command memakai envelope, boot, revision, nonce, dan assignment token yang telah ditahan worker; runtime tidak memilih object key atau menerima kredensial KMS/object store. Pemanggilan kedua atau kegagalan handoff menutup lifecycle tanpa retry download/runtime.

Transport binary memakai origin tetap, HTTPS (loopback HTTP hanya fixture), no redirect, `Accept-Encoding: identity`, respons `application/octet-stream` dengan `Cache-Control: no-store`, exact `Content-Length`, dan deadline bersama credential/request/body sesuai `http.timeoutMs` (100–3000 ms). Payload harus berukuran tepat `grant.plaintextBytes` (maksimum 1 MiB); plugin maksimal 16 MiB. Digest, package/version, runtime, permission, dan seluruh file plugin divalidasi sebelum callback. `inputDigest` adalah identitas canonical request, bukan hash byte plaintext; integritas plaintext/AEAD tetap diverifikasi coordinator sebelum delivery. Endpoint coordinator tetap draft dan belum terdaftar pada `AppModule`.

`inputs.payload` dan `inputs.plugin` adalah byte buffer pinjaman. Worker menghapusnya saat abort dan setelah callback settle, juga saat download/validasi berikutnya gagal. Chunk parsial dihapus pada timeout/abort. Ini tidak menghapus copy, string, file materialisasi, atau buffer milik SDK yang dibuat trusted bridge; bridge/sandbox memiliki cleanup dan retention untuk salinan tersebut. Callback tetap harus memakai `context.runStep()` pada setiap dispatch I/O berikutnya dan menghormati abort setelah await. Hasil callback yang sudah in-flight tetap dapat kembali sebagai evidence setelah stop; bukan completion durable. Tidak ada parser prompt atau plugin execution otomatis pada host.

Pilihan adapter sandbox tetap O03. [Evaluasi sandbox](../security/SANDBOX-EVALUATION.md) mencatat input deployment, kandidat, dan eksperimen keamanan/recovery yang harus dibuktikan sebelum adapter produksi dipilih.

## Pemeriksaan fondasi M3

### Worker HTTP dengan dua coordinator dan shared storage

`npm run test:runner:http` menjalankan `RunnerWorker` melalui proxy loopback ke dua proses API Nest/Fastify independen yang memakai PostgreSQL dan Redis nyata. API memakai `AppModule` dengan role `api-production` (tanpa Contract Lab), tetapi authentication tetap fixture `m0-local`, bukan OIDC produksi. Fixture memasok credential acak, connection runner-local, admission dengan hold 10 unit, dan synthetic dispatch-envelope metadata. Runtime dan driver sandbox tetap fixture inert; payload/KMS/plugin download tidak dilakukan pada proof ini.

Lima skenario memeriksa: ACK claim hilang lalu API A exit dan worker melanjutkan scope/nonce yang sama di B; cancel melalui B menolak paid step berikutnya di A sambil mempertahankan hasil call in-flight; penghapusan lease key Redis menolak recreate, lalu reaper API membuat durable fence dan mempertahankan hold/late evidence; ACK proposal hilang sesudah commit PostgreSQL tanpa proposal/runtime kedua; serta lost committed evidence ACK dengan encrypted spool reopen/replay melalui B dan dedup quarantine PostgreSQL. Skenario spool berjalan pada Linux. Fence wait memakai 25 detik: eligibility query `assignment.updated_at + 15s`, interval scan 5 detik, dan allowance scheduling/DB CI 5 detik. Ini bound fixture, bukan SLO produksi. Assertions memisahkan proposal dari completion, quarantine dari verified usage/ledger, serta local stop dari remote outcome. New-boot worker tidak memperoleh automatic replacement atas execution yang fenced.

Jalankan hanya dengan **PostgreSQL dan Redis disposable**, karena dua API memakai recovery workers nyata yang memindai active assignments. Harness menuntut flag eksplisit, membatasi proses dan timeout, menutup worker/API/proxy saat teardown, serta menghapus row/key milik UUID fixture saja; tidak memakai FLUSHDB atau mereset global epoch. CI quality menjalankan gate ini sesudah Redis primitive conformance. Setelah environment disposable dikonfigurasi melalui [configuration guide](CONFIGURATION.md):

```powershell
$env:M0_RUNTIME_MODE = 'm0-local'
$env:M3_COORDINATION_REDIS_URL = 'redis://127.0.0.1:6379/13'
$env:M3_WORKER_HTTP_DISPOSABLE = '1'
npm run test:runner:http
```

Ini proof integrasi worker/control-plane dengan shared storage pada local fixture mode. Strict nonlocal epoch recovery, Redis restart/failover, node/worker-process crash, sandbox containment, live provider/Claude, encrypted payload/plugin production wiring, production collector lifecycle/KMS/storage recovery, stop receipts, dan completion/settlement tetap membutuhkan gate terpisah. Collector-only SIGKILL proof di unit suite tidak menggantikan worker/node crash gate.

Worker juga menolak assignment ID berbeda untuk execution/attempt yang identitasnya masih ditahan. Replacement membutuhkan durable fencing, effect reconciliation, dan retirement protocol; bootstrap ini tetap tidak mengaktifkan automatic reassignment.

Harness lifecycle satu assignment dapat dijalankan tanpa PostgreSQL/Redis atau provider:

```powershell
npm run test:runner:lifecycle
npm run test:runner:worker
```

Tes lifecycle mencakup aktivasi/renewal, guarded runtime step, cancel saat startup, lease loss, startup deadline, late cleanup yang tetap `UNCONFIRMED`, dan hasil efek in-flight. Tes worker mencakup heartbeat/claim/report dan binary delivery lewat HTTP loopback dengan runtime/sandbox fixture, duplicate/lost acknowledgements, scope checks, capacity, presence expiry, shutdown signal, serta drain deadline. Handoff fixture mengunduh payload dan paket pinned, mematerialisasi file inert pada temporary private root, dan membuktikan penghapusan byte buffer. Tes fault mencakup metadata/ukuran/digest invalid, stalled body/credential, cancel/expiry selama delivery, concurrent handoff, dan larangan dispatch sesudah gagal. Ini belum menguji worker terhadap live coordinator/Redis/PostgreSQL, KMS/trust produksi, atau isolasi sandbox. Seluruh regresi komponen runner juga berjalan melalui `npm run test:unit`.

Di terminal terpisah setelah database siap:

```powershell
npm run test:m3:foundation
npm run test:integration
```

Tes di atas membuktikan admission envelope, pull claim, exact runner lease, epoch fence, scoped payload-read authorization, tool-effect intent/status recovery dengan receiver fixture, registry plugin dengan signature Ed25519 nyata dan test signing key, delivery yang menolak revokasi selama download, serta validasi/materialisasi file paket plugin ke direktori sementara. Reader S3 diuji dengan stream fixtures untuk ukuran palsu, truncation, timeout, dan abort. Tes integrasi M1 membuktikan profile pinning, snapshot, dan revocation fence sebelum admission; dispatch claim mengirim metadata paket tanpa object key. Mereka tidak menjalankan Claude SDK, kode plugin, trust-root produksi, atau sandbox. `npm run test:runner:redis` perlu Redis terpisah pada `M3_COORDINATION_REDIS_URL`; `npm run test:dispatch:s3` dan `npm run test:plugin:s3` perlu object store S3-compatible disposable sesuai workflow CI. Jangan mengarahkan tes itu ke service/data produksi. Format signature dan batas production wiring ada pada [plugin contract](../contracts/TOOLS-PLUGINS.md#signature-dan-delivery-internal-v1).

Status dan gap terbaru ada di [CURRENT-STATE](../implementation/CURRENT-STATE.md), [PLAN](../PLAN.md), dan [acceptance gates](../testing/ACCEPTANCE.md).
