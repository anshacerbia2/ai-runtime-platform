# Acceptance, Conformance, dan Production Gate Catalogue

**Baseline target G01–G39, implementation scope reconciled 25 September 2026.** Sejumlah local unit/integration/browser gates sudah dijalankan; full provider/runtime/production scenarios tidak otomatis lulus. Catalogue ini mendefinisikan acceptance requirements. Rincian hasil harus merujuk revisi dan environment pada evidence, bukan status blanket NOT RUN atau PASS.

## 1. Gate protocol

Setiap test merekam ID, invariant, build/runtime/profile digest, environment, fixtures, fault/load parameters, expected assertion, observed result, trace/log/ledger evidence reference, timestamp, dan reviewer. Artifact evidence harus immutable/scoped. Unit test, adapter fake test, integration test, live smoke test, dan chaos test dibedakan.

Applicable tests wajib pass sebelum production cutover. N/A hanya untuk capability yang benar-benar tidak dipakai dan disetujui reviewer; direct-chat pilot tidak otomatis mewajibkan plugin runtime, tetapi ledger/auth/SSE/route gates tetap berlaku. Principal source sign-off bukan runtime evidence.

## 2. Catalogue

`npm run test:runner:http` adds a shared-store worker composition gate: two independent full Nest/Fastify API processes, PostgreSQL reservations/authority, Redis presence/leases, and a real loopback proxy. Four fault scenarios cover lost claim ACK plus API A exit/B continuation without duplicate assignment/runtime, cancel through B denying a new worker step through A, missing lease key followed by actual API reaper fencing and late evidence intake, and lost proposal ACK after PostgreSQL commit without automatic retry. Assertions retain nonzero budget holds, quarantine unverified evidence without ledger writes, and deny automatic replacement after fence. Authentication is local fixture mode and sandbox/runtime are inert fixtures. This extends local G04/G05/G12/G21/G29/G30/G35 subsets; it does not close full Redis restart/failover, strict nonlocal epoch, worker/node crash, production auth, payload/KMS/plugin delivery, sandbox/Claude, reporting durability, completion or settlement gates. The harness requires explicit disposable PostgreSQL/Redis opt-in and performs only fixture-scoped row/key cleanup.

The 19 October authority/reporting subset covers fresh coordinator preflight before worker external steps, durable rejection during periodic renewal, late acknowledgements after stop, a sealed runtime context during result delivery, one result proposal without runtime replay, and late quarantine evidence with bounded concurrency. A TDD regression proves pending evidence cannot permit another paid dispatch. The worker loopback fixture reaches HTTP input handoff, authority checks, evidence intake, proposal and cleanup. A separate PostgreSQL fixture proves cancel-before-proposal rejection and proposal-before-cancel remaining RUNNING, rejects renewal after cancel, deduplicates old-assignment evidence after durable fencing, and asserts intake creates neither verified observations nor ledger entries. This extends local G05/G12/G21/G35 subsets; it does not prove atomic cancellation of remote effects, a durable reporting spool, full worker-to-live-coordinator/Redis integration, finalization, settlement, or sandbox/runtime production gates.

The 19 October worker handoff adds local G05/G30/G32 subsets: exact retained lease/envelope commands, one-use input callback after STARTED, pinned plugin validation, strict bounded binary transport, cancel/expiry during delivery, failure sealing, borrowed-buffer erasure, and preservation of eventual in-flight callback evidence. The worker loopback fixture downloads payload/plugin and materializes inert files in a temporary private root. This is HTTP composition with a fixture coordinator/driver/runtime, not production endpoint activation, KMS/signer trust, sandbox isolation, durable completion, or live Redis/PostgreSQL worker proof. The standalone payload client relies on coordinator AEAD/plaintext verification; canonical `inputDigest` is not a wire byte checksum.

The local single-assignment lifecycle harness (`npm run test:runner:lifecycle`) composes the lease HTTP client, monotonic gate, renewal/watchdog loop, and sandbox supervisor. A loopback HTTP fixture verifies exact command renewal while trusted runtime work is in flight. Fault tests cover cancellation during activation/launch, lost renewals, expiry, launch timeout, quiesce, late acknowledgements, and preservation of in-flight effect results. The worker bootstrap harness (`npm run test:runner:worker`) adds separate heartbeat/claim loops, exact STARTED acknowledgement before fixture runtime dispatch, one lifecycle/nonce per replayed assignment, local capacity, process-presence expiry checks, host shutdown signals, and a non-extensible drain deadline. These extend local G05/G29/G30 subsets; the coordinator and driver/runtime remain fixtures, with no real isolation, live Redis/PostgreSQL worker recovery, deployment bootstrap, durable cancel/result/evidence delivery, stop receipt, reassignment, or external-effect reconciliation proof.

## 3. Calibrated principal scenarios

Worker candidate H=5s/L=15s/R=5s. Define t0 as kill injection, last confirmed renewal, scheduler/network allowance delta, and measured orphan detection time. Nominal L+R=20s excludes delay; test threshold must include predefined justified delta and observed environment. Do not move goalposts after measurement.

SSE test records retention age plus byte caps and earliest cursor. Budget race includes balance conservation, not only HTTP counts. Late-usage test compares expected fixture charges and unresolved cases; one matching fixture is not universal 100% accuracy. Sandbox test checks actual host/control secret isolation, not merely whether one path returns Permission Denied.

## 4. Quality fitness functions

App owners provide golden datasets/acceptance criteria for fare interpretation, translation/verification, RAG citations/ACL, and document rendering. Measure cost per accepted output, repair/retry rate, and latency distributions. Model/provider upgrade reruns affected fixtures. Scores/thresholds belum diberikan sumber; O08 blocks cutover until approved.

## 7. Launch blockers

Any stale write after durable fence, duplicated stateful effect from platform retry, budget denial mutation, duplicate credit, cross-application leak, web authentication/session bypass, unbounded agent credential access, or fabricated zero usage blocks launch. Missing required parameter/credential/data-policy/rollback decision also blocks launch.

Performance misses are assessed against pre-agreed SLO/error budget; safety misses are not waived by average good performance. Every release repeats impacted gates, not necessarily all unrelated capabilities.
