# M1 — Durable Control Plane Foundation

**Status:** LOCAL IMPLEMENTATION COMPLETE for the P1 test scope; **not production-ready**. The durable control-plane, identity boundary, admission/accounting foundation, and applicable P1 acceptance tests are implemented and proven against the local PostgreSQL environment. External/nonlocal integration evidence remains pending.

## Implemented foundation

M1 now provides:

- durable Application Registry with Keycloak client mapping and revision/CAS lifecycle;
- AI Connection Registry, Credential Instance metadata, and application/profile Credential Bindings;
- dedicated/shared connection semantics with explicit shared quota groups;
- immutable/revisioned Execution Profiles plus alias/rollback control;
- separate application, operator/admin, and runner principals;
- local principal verifier for development and a production-capable OIDC/JWKS verifier using configured issuer, audience, azp, signature, expiry/nbf, roles, and scopes;
- operator-only control-plane mutations and audit entries;
- durable execution admission with application-scoped idempotency, immutable profile snapshot, initial attempt, reservations, and transactional outbox;
- durable cancel intent that does not fabricate completion or zero cost;
- budget accounts, deterministic multi-account locking, reservations, usage observations, append-only ledger adjustments, overage state, and durable projections;
- unknown usage remains null/unknown rather than being converted to zero;
- inbox/outbox idempotency foundation;
- application-scoped artifact metadata without P3 object-store execution;
- durable runner pool/node registration metadata, authenticated runner ownership, and operator lifecycle (RUNNING/DRAINING/DISABLED);
- application-scoped reads and cross-application denial;
- operator Control Plane admin console with resource views for Applications, AI Connections, credential metadata/bindings, profiles/aliases, budgets, runner pools/nodes, and secret-free snapshots;
- Next.js App Router and standalone entry with server-owned OIDC Authorization Code + PKCE, nonce/state verification, refresh, app-local logout, and authenticated server-rendered docs;
- opaque signed cookies backed by encrypted Redis session records, with refresh locks and logout-safe compare-and-set updates;
- CDD/token-driven UI shell with reusable design-system primitives/components/compositions and mechanical token-bypass enforcement;
- additive migrations 0002–0006, including contract receipts and runner authority; existing M0 data is preserved.

No provider/model call or agent execution is enabled by M1.

## Identity and hosting boundary

m0-local remains supported for Contract Lab development. In that mode the web BFF requires distinct local application/operator tokens; runner credentials are separate fixtures. None is used in m1-oidc, which requires a real session. Redis-backed web sessions do not implement runner hot state. The deployment and verification recipe is in [Web/BFF Operations](../development/WEB.md).

m1-oidc activates the nonlocal identity/hosting contract. Configuration is fail-closed and includes:

- the platform's own public origin, with no mount prefix;
- dedicated confidential OIDC client metadata, distinct per environment;
- exact callback/logout values under that origin;
- trusted OIDC issuer/audience/JWKS endpoint;
- web-only confidential-client secret and session-store encryption/signing key;
- explicit session Redis, lifetimes, lock bounds, API origin, and document root.

The per-app ATI One proxy credential is retired by [ADR-0025](../adr/0025-external-app-standalone-auth.md).

The OIDC verifier resolves an application only through the durable Application Registry. An operator token cannot become an application caller and an application token cannot acquire operator authority.

## Data and secret safety

Provider credential material is not accepted from application requests and is not returned by API/UI/log views. The durable credential table stores metadata/reference only. Actual Vault/secret-manager/workload-identity integration remains deployment-specific and is not falsely claimed as implemented.

M1 migrations are additive. M0 contract history remains intact and M0 provider-call count remains zero.

- live Keycloak client/realm/JWKS integration and actual token flow;
- deployed BFF behavior against the actual Keycloak client, HTTPS ingress, and protected Redis session store, including callback/logout registration, replica failure, and key rotation;
- concrete Vault/secret-manager/workload-identity product and rotation process;
- Redis-backed runner heartbeat/hot-capacity tier and derived OFFLINE behavior in a deployed environment;
- nonlocal deployment, restore/rollback, operational ownership, production SLOs/retention, and signed reviewer gate evidence;
- P2 provider adapters and P3 runtime/placement are intentionally outside M1.

Production readiness still follows P3.5 and the full Acceptance Catalogue.
