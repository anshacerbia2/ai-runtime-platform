# Sandbox adapter evaluation for M3

**Status: working evaluation, not a technology decision or production approval.** [ADR-0011](../adr/0011-sandbox-security.md) fixes the isolation requirements; [O03](../decisions/OPEN-QUESTIONS.md) leaves the concrete runtime open. This page gives security and runtime owners a repeatable way to choose and verify an adapter. A local `LocalSandboxSupervisor` is only a lifecycle port and does not satisfy this gate.

## Decision inputs

Target deployment yang dinyatakan owner pada 19 Oktober 2026 adalah **Linux VM/VPS**. Kandidat uji pertama adalah gVisor `runsc` dengan `systrap`, sesuai [platform guidance untuk VM](https://gvisor.dev/docs/user_guide/platforms/). Ini mempersempit eksperimen O03; bukan penetapan distro/arsitektur VPS, provider, region, threat tier, resource production, atau persetujuan runtime untuk data sensitif. ADR-0011 tetap berlaku dan O03 tetap OPEN.

Record these for the actual runner pool before comparing candidates:

| Input                                                                                     | Why it changes the choice                                                                           |
| ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Kubernetes/CRI versus direct VM or bare-metal orchestration; node OS and architecture     | Determines whether a Kubernetes RuntimeClass or a separately managed microVM lifecycle is feasible. |
| Hardware virtualization and nested-virtualization availability on **every** eligible node | Determines whether KVM-backed isolation can run and be recovered after node moves.                  |
| Threat tier of application-owned plugin code and co-tenant data                           | Determines required host isolation and whether sharing a sandbox or node is acceptable.             |
| Claude/agent runtime syscall, filesystem, network, and process needs                      | Determines compatibility under the chosen isolation boundary.                                       |
| Allowed egress, broker endpoints, credential injection, and data region                   | Determines network policy and whether the sandbox can avoid broad secrets.                          |
| Job duration, cold-start budget, memory/CPU/disk/process caps, and concurrent jobs        | Determines measured capacity and denial-of-service limits.                                          |

Do not infer these from local Windows tests or from the existence of a container runtime. In particular, do not install a fallback that silently runs plugin code in the API process or in an ordinary host child process.

## Candidate fit to verify

| Candidate                                 | Useful integration property                                                                                                                                    | Required proof / trade-off                                                                                                                                                                                                                                                                                                                                             |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| gVisor (`runsc`)                          | [Kubernetes RuntimeClass and containerd integration](https://gvisor.dev/docs/user_guide/quick_start/kubernetes/) can preserve a container-oriented deployment. | [Security model](https://gvisor.dev/docs/architecture_guide/security/) and [production guidance](https://gvisor.dev/docs/user_guide/production/) describe syscall interception and workload-dependent overhead. Test actual runtime compatibility and hostile-code containment; the production guide explicitly does not serve as an untrusted-code deployment recipe. |
| Kata Containers                           | [Kubernetes pods can run in a VM-backed boundary](https://github.com/kata-containers/kata-containers/blob/main/docs/design/virtualization.md).                 | Verify [KVM or nested virtualization prerequisites](https://github.com/kata-containers/kata-containers/blob/main/docs/installation.md), guest/image provenance, networking, startup cost, and node-failure cleanup on the intended pool.                                                                                                                               |
| Firecracker with a dedicated orchestrator | A microVM boundary can be managed independently of Kubernetes.                                                                                                 | [Production host guidance](https://github.com/firecracker-microvm/firecracker/blob/main/docs/prod-host-setup.md) requires KVM and a jailer or equivalent controls. The platform would own image, network, lifecycle, discovery, and recovery integration; count that operational scope explicitly.                                                                     |

These are candidates, not ranked defaults. If Kubernetes is the target, compare gVisor and Kata on the same pinned agent/plugin workload and hostile fixtures first. If the runner pool is not Kubernetes, assess the actual orchestration path before treating Firecracker as simpler. No candidate passes because of its product name.

## Linux VM/VPS experiment

The [native cgroup/live-owner crash checkpoint](../development/NATIVE-CGROUP-OWNER-CRASH.md) adds bounded kernel hierarchical population reads, an empty-parent/populated-child experiment, and SIGKILL of a real owner with a surviving attached monitor/sandbox. Stale ownership refuses reopen before and after explicit exact-bound fixture cleanup. This advances live-orphan refusal proof; production whole-host ownership/close, operational takeover, worker fencing, node loss and actual VPS approval remain separate gates.

The driver fixture now uses [native runsc process transport](../development/NATIVE-RUNSC-PROCESSES.md) for fixed commands and attached monitors, with independent executable pin/root checks, bounded output/admission/deadlines and isolated host environment. A real one-second attached-monitor deadline preserves LOST, denies rerun/new reservation and requires explicit kernel-subtree cleanup. This is not a whole-host process-crash takeover or production activation; the full installed package and sidecars still require trusted provenance.

[Pinned rootfs bundle production](../development/VERIFIED-RUNSC-BUNDLES.md) now replaces ad hoc driver fixture bundles. BusyBox bytes have a committed SHA-256 pin; producer/verifier hashes the whole approved file tree, emits fixed OCI policy and rejects tampered bytes before reservation/dispatch. The internal tree digest is not an OCI registry digest or production release approval. Native host CLI/ownership recovery, actual VPS and runtime/credential/egress gates remain required.

The driver fixture now uses the [private file reservation store](../development/RUNSC-LAUNCH-STORE.md) instead of ad hoc markers. Linux tests separately cover storage lock/corruption/bounds and SIGKILL before any runtime spawn; the real-runtime probe checks clean store reopen only after monitor/tree cleanup. Neither establishes production host unlock, image verification, live-orphan crash recovery, volume/node/power-loss safety or actual VPS approval.

[`scripts/probe-gvisor.mjs`](../../scripts/probe-gvisor.mjs) adalah opt-in fixture conformance, bukan installer VPS. [Driver/supervisor lifecycle](../development/RUNSC-DRIVER.md) kini juga diuji dengan real runsc melalui disposable fixture host; production host/worker composition belum diaktifkan. Command fixture saat ini menuntut Linux 5.6+ x64 dengan root dan flag `--disposable-linux-host`; target CI adalah Ubuntu 24.04 x64. Host harus menyediakan cgroup v2 CPU/memory/pids controllers, root-owned binaries, serta static BusyBox. Tidak ada fallback Docker/runc/host-process execution untuk fixture. Trusted CLI `runsc` dijalankan host-side; program fixture hanya berjalan di sandbox.

CI memakai [rilis `release-20261012.0`](https://github.com/google/gvisor/releases/tag/release-20261012.0), paket x86_64 `gvisor-x86_64.tar.bz2` dengan SHA-256 `180dd277f657c1478f09490e8a9a595f7378257510b43d1d3694a769aef9ed02`, diunduh melalui HTTPS dan diverifikasi sebelum ekstraksi. Paket mencakup `runsc` dan `gvisor-bin/` sidecars; [installation guidance](https://gvisor.dev/docs/user_guide/install/) menjelaskan perubahan distribusi multifile. Runtime binary dan BusyBox rootfs fixture di-hash lagi dan dicatat bersama kernel/version/architecture/controller dalam JSON log. BusyBox berasal dari signed Ubuntu package pada image CI; fingerprint dicatat, tetapi ini belum approved/pinned production agent image atau supply-chain gate plugin.

Konfigurasi eksperimen tetap: `--platform=systrap --network=none`, rootfs read-only, UID/GID 65532, no-new-privileges, capability sets kosong, tanpa host bind mount/socket/hook, tmpfs `/tmp` 8 MiB dengan noexec/nodev/nosuid, memory cgroup 256 MiB, pids 32 dan CPU quota 50000/100000. Nilai tersebut hanya fixture limits. Probe membaca nilai cgroup yang diterapkan dan memeriksa oversize tmpfs write gagal; ini belum load/neighbor/OOM/fork-exhaustion acceptance untuk workload produksi.

Empat eksperimen menjalankan ordinary exit; concurrent same-ID create yang menyisakan tepat satu container; state observation dari proses CLI baru, duplicate-start rejection, exact fixture annotations, basic environment/filesystem/no-external-network checks dan graceful stop; lalu TERM-ignoring parent/child dengan forced all-process KILL. TERM ACK sendiri harus meninggalkan fixture running. Probe mempertahankan attached `runsc run` parent/waiter untuk setiap fixture yang mengeksekusi program, dan memeriksa exit code 0/143/137 sesuai kasus. Setelah monitor selesai, probe memerlukan runtime delete berhasil, tidak ada proses di seluruh subtree cgroup yang dimiliki, dan container tidak lagi terdaftar. Missing state atau ACK tidak dijadikan stop proof. Jika cleanup gagal, probe gagal dan mempertahankan workspace untuk inspeksi; tidak menghapus runtime metadata yang belum terkonfirmasi bersih.

Pinned `runsc list --format=json` memakai `null` untuk daftar kosong; parser menerima bentuk itu secara eksplisit dan tetap menolak output malformed. Runtime juga menyimpan bind-mounted `null-netns` di private state root. Setelah semua container/cgroup milik probe bersih, cleanup memverifikasi absolute owned workspace dan hanya meng-unmount cache tersebut sebelum menghapus workspace. Error utama dan cleanup dipertahankan bersama agar kegagalan containment tidak tertutupi error teardown.

Eksperimen awal mereproduksi fast-exit race: detached create/start diikuti `wait` dari proses lain dapat menjawab exit status unavailable setelah sandbox berhenti. Attached monitor dipertahankan agar status tersebut benar-benar diamati oleh parent-nya. Driver kini mempertahankan uncertainty dan memakai independent termination evidence; production host recovery setelah monitor/host crash tetap belum dibuktikan. Tidak ada fallback yang menebak exit code atau menyamakan missing state dengan successful completion.

Rootfs write probe sengaja memakai directory DAC-writable agar kegagalan tidak hanya disebabkan UID nonroot. Host canary file/environment, symlink escape menuju canary, runtime socket absence, IPv4/IPv6 loopback-only routes dan metadata-IP connection rejection adalah containment checks dasar. `network=none` tetap mempunyai guest-local loopback sesuai [networking contract](https://gvisor.dev/docs/user_guide/networking/); parser menolak external/default route dan interface selain loopback, bukan menuntut tidak ada route sama sekali. Ini **bukan** penetration test lengkap, egress allow-list untuk broker, compatibility Claude/Node/native dependencies, multi-app hostile workload, hard supervisor crash/lost-ACK injection, node loss, disk/power-loss recovery, lease/fence integration atau izin retirement/reassignment. Binding fixture memakai UUID sintetis dan bukan assignment platform yang aktif.

Recipe pada disposable Linux VM yang sudah dipersiapkan:

```sh
npm ci
npm run build -w @ai-runtime/runner
sudo -n /absolute/path/to/node scripts/probe-gvisor.mjs \
  --disposable-linux-host /absolute/path/to/runsc /absolute/path/to/static-busybox
```

Atau `npm run test:sandbox:gvisor -- --disposable-linux-host ...` dari sesi root yang memang diotorisasi untuk host disposable tersebut. Command tidak memasang paket atau mengubah daemon host; workflow CI memasang runtime hanya pada ephemeral runner-nya sendiri. Tidak ada credential/data aplikasi, provider call atau Claude runtime. JSON `ai-runtime-gvisor-conformance/v1` mencatat outcome dan fingerprint dalam job log. Unit policy tests berjalan di Windows/Linux melalui tooling suite; real-runtime evidence hanya berasal dari job `gvisor-conformance` pada commit yang sama. Pass di GitHub-hosted VM tidak menggantikan pengujian VPS yang akan dipakai pilot.

## Common acceptance experiment

For each candidate, record pinned runtime/image/package digests, host/kernel/CRI versions, node topology, applied policy, workload digest, observed behavior, logs, and reviewer disposition. Evidence must be from the deployment shape proposed for production, not only a local fake driver.

1. Launch an exact assignment twice after a response loss and after supervisor restart. The adapter's `recover` lookup must return the full recorded binding and handle for the deterministic sandbox identity; only one owned sandbox may execute. A stale boot, owner, generation, or epoch cannot stop or attach to a different sandbox. Driver conformance now tests same-assignment supervisor replacement/no-rerun with real runsc and private file reservations. Hard process/node crash, production lock recovery and worker/shared-store lost-ACK composition remain separate proof.
2. Try to read host/control-plane environment, service-account material, runtime sockets, arbitrary host paths, and another application's workspace. Test symlinks and mount propagation. The workload must receive no broad host/provider credential.
3. Probe metadata and private/control networks over IPv4 and IPv6, DNS changes, and redirects. Only explicit broker/approved destinations may be reachable. Verify outbound policy at the enforcement point, not through agent SDK prompts.
4. Exercise CPU, memory, process, disk, log, and wall-clock exhaustion. Measure whether neighboring jobs and the control plane remain within their stated budgets.
5. Quiesce new launches while an assignment runs; keep its declared in-flight deadline, then explicitly stop it. Exercise graceful stop, force escalation, supervisor crash, and node loss while child processes and an external operation are active. Inspect the entire owned sandbox/process tree. Record local termination separately from remote effect and usage reconciliation; never authorize reassignment solely from a successful signal.
6. Verify pinned image/package provenance, read-only base, bounded writable workspace, cleanup and retention behavior. Capture startup and steady-state latency/capacity against workload-specific thresholds chosen by the owners.

Map the resulting artifacts to [G18/G19/G24 and recovery gates](../testing/ACCEPTANCE.md). A failure or missing inspection is `UNCONFIRMED`; it does not become a successful stop receipt. Selection also needs the deployment owner, security reviewer, credential agreement, data policy, and recovery plan required by [SECURITY](SECURITY.md).
